## Purpose

This document defines how the MVP database is populated for local development, testing, and the M3 usability prototype without using production private data. It separates baseline seed data from environment-specific test data and establishes a clear boundary between synthetic and real user data.

## Data Categories

| Category | Purpose | Environment |
|---|---|---|
| Baseline seed | Public recipe and reference data required for discovery | All non-production and migration baseline |
| Development seed | Synthetic demo accounts, pantry, plans, lists, and recommendations | Local development |
| Test data | Deterministic fixtures for automated tests | CI and local tests |
| Usability data | Synthetic consented scenarios for the M3 prototype | Prototype and usability sessions |
| Production data | Real user and business data | Production only |

Production data is never used as seed, test, or usability data.

## Baseline Seed Data

Baseline seed data is delivered through migrations (M5-002 version `00002`) and is idempotent.

### Recipe baseline

- A curated set of public recipes that demonstrate Indonesian kitchen vocabulary, varied preparation times, and ingredient categories used by the MVP personas (Sarah and Daniel).
- Each recipe must be complete enough to cook, with ingredients, instructions, servings, and preparation time.
- Recipes are public by default and marked with `is_public = true`.
- The baseline is reviewed for quality by Culinary Knowledge and Recipe Experience; it is not generated by AI.

### Reference vocabulary

- Pantry ingredient categories used by the MVP.
- Meal occasions (e.g., breakfast, lunch, dinner).
- Cooking constraint and preference vocabulary used by recommendation context.

Baseline seed must be reviewed and stable; it is not replaced by test data.

## Development Seed Data

Development seed is created by a script (not a migration) and resets to a known state for local work.

### Synthetic demo profiles

- Two demo profiles aligned to the personas: one time-pressured cook (Sarah) and one speed-focused shopper (Daniel).
- Each profile has a pantry with items across categories, some approaching expiry, and explicit preferences and constraints.

### Scenario data

- A daily and weekly meal plan with planned meals.
- A shopping list generated from meal intent and pantry gaps.
- A kitchen recommendation with options and rationale for a representative context.

Seed scripts must be reproducible and leave no reference to production data. All values are clearly synthetic.

## Test Data

Test data is deterministic and created per test or per suite to verify specific behavior.

### Fixtures

- Fixtures are defined in code or SQL for each query contract in M5-003.
- Each fixture asserts the exact state a query or repository expects.
- Soft-delete and timezone boundary cases are explicitly covered (for example, an item deleted before the query filter, and a meal date on the user's local boundary).

### Isolation

- Tests run against a disposable database or schema created from the full migration chain.
- No test writes to a shared or production database.
- Parallel tests do not share mutable fixture state that could cross-contaminate ownership assertions.

### Timezone fixtures

- Date-bounded queries are tested with a user timezone other than the server default to prove M4-DEC-007 handling.
- Meal date and expiry boundary cases use the user local date boundary.

## Usability Prototype Data

- The M3 prototype uses synthetic or consented data only, as required by M3 sign-off assumptions.
- Prototype data never includes production private data, real user preferences, or real pantry contents.
- Prototype scenarios mirror the persona journeys so findings are transferable to implementation without exposing real data.

## Data Security Rules

- No seed, test, or fixture file contains credentials, provider secrets, prompts, or personal data of real people.
- Demo account passwords are hashed with the same Argon2id policy as production but use clearly synthetic values.
- Any data that could be mistaken for real user data is marked synthetic and generated programmatically.

## Environment Strategy

| Environment | Source | Reset policy |
|---|---|---|
| Local development | Migrations + development seed script | Full reset on demand |
| CI | Migrations + test fixtures | Full rebuild per run |
| Review/preview | Migrations + curated baseline seed | Rebuilt per environment |
| Usability prototype | Migrations + usability seed | Rebuilt per session |
| Production | Migrations + baseline seed (if promoted) | Versioned, never reset |

## Exit Criteria

M5-004 is complete when:

- Baseline, development, test, and usability data categories are defined and separated.
- Recipe and reference seed is scoped and reviewed.
- Test fixtures cover the M5-003 query catalog including soft-delete and timezone cases.
- Data security and isolation rules are explicit.
- No production data path exists into seed, test, or usability data.
