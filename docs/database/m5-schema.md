## Purpose

This document defines the concrete PostgreSQL schema for the DapurPintar AI MVP. It translates the approved conceptual and logical model into actual tables, columns, constraints, and indexes, preserving aggregate ownership and bounded-context boundaries defined in the Database Design and Tactical DDD documents.

This is the authoritative schema baseline for Goose migrations, SQLC queries, and backend repositories in M7.

## Schema Baseline

### Adoption from decision records

| Decision | Applied here |
|---|---|
| M4-DEC-006 | Single schema, aggregate-owned tables, UUID primary keys, `timestamptz` audit columns, soft-delete only where Database Design calls for it |
| M4-DEC-007 | Instants stored as `timestamptz` in UTC; user timezone in User Profile; meal dates and expiry evaluated in user local date |
| M4-DEC-013 | Recommendation Conversation retained only for active Recommendation; no raw prompt/payload storage |

### Global conventions

- Single database `dapurpintar` with single schema `public`.
- Primary keys are `UUID` (`uuid` type) generated by the application or `gen_random_uuid()`.
- All instants use `timestamptz`.
- Every table includes `created_at timestamptz not null default now()` and `updated_at timestamptz not null default now()`.
- Every table has an ownership marker in documentation and, where useful, a `scope_owner` reference to the owning bounded context's root.
- Soft-delete uses a `deleted_at timestamptz` nullable column. Queries must filter `deleted_at is null` by default. Soft-deleted rows never appear active in business views.
- Foreign keys between bounded contexts are stored only for business identity references, never as ownership of child entities.
- Text columns that represent enum-like lifecycle status use PostgreSQL `text` with `check` constraints in the MVP to avoid migration friction, unless a dedicated enum type adds clarity.

## Aggregate Tables

### Identity and Access - Account

#### `accounts`

Owning bounded context: Identity and Access. Aggregate root.

| Column | Type | Constraints | Meaning |
|---|---|---|---|
| id | uuid | PK default gen_random_uuid() | Business identity |
| email | text | not null unique | Trusted contact and login identity |
| password_hash | text | not null | Argon2id hash; never plaintext |
| status | text | not null default 'pending' check (status in ('pending','active','restricted','closed')) | Account lifecycle |
| timezone | text | not null default 'Asia/Jakarta' | User timezone for date interpretation (M4-DEC-007) |
| email_verified_at | timestamptz | null | When email verification completed (subject to M4-DEC-001) |
| created_at | timestamptz | not null default now() | Creation instant |
| updated_at | timestamptz | not null default now() | Last update instant |
| deleted_at | timestamptz | null | Soft delete for restricted/closed processing |

Indexes:

- `accounts_email_idx` unique on `email` where `deleted_at is null`.
- `accounts_status_idx` on `status` for account lifecycle queries.

## Constraints Summary

### Check constraints

- `accounts.status` restricted to lifecycle values.
- `user_profiles.status`, `preference_sets.status` restricted to lifecycle values.
- `pantry_items.quantity >= 0`, `pantry_items.status` restricted.
- `recipes.servings > 0`, times non-negative, `recipes.status` restricted.
- `recipe_favorites.status` restricted.
- `meal_plans.period_end >= period_start`, `meal_plans.status` restricted.
- `planned_meals.status` restricted.
- `shopping_lists.status` restricted.
- `shopping_items.quantity >= 0`, `source`, and `status` restricted.
- `kitchen_recommendations.status`, `recommendation_options.status` and `position > 0` restricted.
- `recommendation_conversations.status` restricted.

### Uniqueness

- `accounts.email` unique (active rows).
- `user_profiles.account_id` unique.
- `pantries.user_profile_id` unique.
- `recipe_favorites (user_profile_id, recipe_id)` unique among active favorites.
- `recommendation_conversations.recommendation_id` unique (one conversation per recommendation).

### Referential integrity

Foreign keys preserve ownership boundaries. A child entity is owned by its aggregate root through a required FK. Cross-context references (recipe to planned meal, pantry item to shopping item, recommendation to meal plan/shopping list) are stored as business identity references only and are nullable where the relationship is optional.

## Indexing Strategy

### Query-driven indexes

- Unique lookup by business identity uses the primary key.
- All aggregate-to-child navigations are covered by a FK index on the child table.
- Date-bounded views (meal dates, expiry) are indexed so daily and weekly queries stay stable.
- Public recipe discovery uses the `(is_public, status)` index.
- Favorites deduplication uses the partial unique index.

### Index discipline

- No index is added speculatively. Every index maps to a documented query or a referential integrity requirement.
- Partial indexes are preferred for soft-delete filters to keep active scans small.
- JSONB columns (`preferences`, `ingredients`, `instructions`, `context_reference`, `context_snapshot`) are not indexed in the MVP unless a query requirement emerges; they are application-shaped.

## Timezone Handling (M4-DEC-007)

- All `timestamptz` values are stored in UTC by PostgreSQL.
- `accounts.timezone` (default `Asia/Jakarta`) is the authoritative user timezone.
- `user_profiles.timezone` is an optional override.
- `expiry_date` and `meal_date` are stored as `date` in the user's local date boundary.
- All date-bounded queries must receive the user timezone and compute the boundary before execution. Server-UTC defaults are prohibited for user-visible date logic.

## Retention Handling (M4-DEC-013)

- Raw provider prompts and payloads are never stored.
- `recommendation_conversations.context_snapshot` holds only the bounded business context.
- `expires_at` is set when a conversation is created or closed; cleanup runs delete or anonymize past the retention window.
- Durable recommendation meaning lives in `kitchen_recommendations` and `recommendation_options`, not in conversation text.

## Seed and Test Data Boundary

Seed and test data are described in M5-004. Schema-level notes:

- Test data must use synthetic or consented data, never production private data.
- Foreign keys must be satisfied in dependency order during seeding (accounts -> profiles -> pantries -> ... -> recommendations).

## Exit Criteria

M5-001 is complete when:

- Every aggregate root and child entity from Database Design has a concrete table.
- Every lifecycle status is constrained.
- Ownership and cross-context references follow the approved boundaries.
- Decision records M4-DEC-006, M4-DEC-007, and M4-DEC-013 are applied.
- Every index maps to a documented query or integrity requirement.
